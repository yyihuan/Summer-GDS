## 1. 文档概述

### 1.1 文档目标

本文档用于整理 Summer-GDS 重构后的需求边界，作为后续重新设计前后端和 YAML
协议的依据。

本文档只保留当前已经达成一致的需求，不再机械继承旧实现中的历史包袱。

当前 MVP 的正式实现范围以 `docs/refactor/yaml-protocol.md` 为准：只支持
`base_shape` 的 polygon/circle、polygon 圆弧倒角和 GDS 输出。`rings`、`via`、
`gds.scale`、字符串顶点输入均属于后续迭代或前端转换能力，不是当前后端 YAML 协议。

### 1.2 产品定位

Summer-GDS 的主要用户是 GUI 用户，核心使用方式是：

- 用户通过 GUI 编辑图形配置
- GUI 生成规范 YAML
- 后端根据 YAML 生成 GDS

因此：

- GUI 是主入口
- YAML 是正式配置协议，同时承担导入导出和持久化作用
- 直接手写 YAML 批量生成不是当前重点

## 2. 系统架构

### 2.1 前后端职责分离

**前端负责：**

- 提供易用的输入方式
- 做单值输入、简化模式、批量填充等交互
- 将简化输入展开为无歧义的正式 YAML

**后端负责：**

- 读取结构稳定的 YAML
- 执行几何生成
- 生成 GDS

结论：后端不接受复杂字符串规则，不承担含糊输入的推导责任，正式 YAML
必须是展开后的明确结构。

### 2.2 对象模型

长期产品可按三类产品语义组织，后端按几何原语实现：

| 前端对象     | 产品语义               | 后端原语      |
| ------------ | ---------------------- | ------------- |
| `base_shape` | 基础光刻图形（实心）   | `solid`       |
| `rings`      | 基础光刻图形（多环）   | `ring_array`  |
| `via`        | 工艺处理图形（单环）   | `single_ring` |

后端建议拆成两层：

- **基础几何层**：`polygon` / `circle`
- **生成操作层**：`solid` / `single_ring` / `ring_array`

当前 MVP 只实现 `base_shape`。这样可以先验证结构化 YAML、几何渲染、倒角和 GDS
写入链路；`rings` 和 `via` 进入实现前需要单独补齐协议、几何和测试。

## 3. 数据协议

### 3.1 顶层 YAML 结构

保留三段顶层结构：

```
global   ← 全局默认设置、图层映射等
gds      ← 输出相关配置
shapes   ← 形状定义
```

YAML 是正式协议，字段类型必须稳定、明确。

### 3.2 图层格式

图层格式必须是：

```yaml
layer: [layer_num, datatype]
```

不接受将字符串 layer 名称直接作为 `shape.layer`。

### 3.3 `layer_mapping`

`layer_mapping` 用于保存 `layer_num`、`datatype`、`layer_name`
的映射关系，用途包括：

- GUI 显示图层名称
- 提高 YAML 可读性
- 后续做图层管理

注意事项：

- 标准 GDSII 本体只保存 `layer` 和 `datatype`，`layer_mapping`
  不能假设被标准 GDS 软件自动识别
- 当前阶段 `layer_mapping` 只作为本软件自用的 YAML 配套文件
- 暂不做 KLayout 专有兼容

`layer_name -> [layer_num, datatype]` 映射能力当前优先级较低，建议预留设计。

## 4. 基础几何规则

所有形状共享以下几何基础规则。

### 4.1 几何类型

当前支持两种基础几何定义方式，未来可扩展其它生成器，本期不做。

**`polygon`** — 显式顶点输入：

```yaml
vertices:
  - [0, 0]
  - [10, 0]
  - [10, 10]
  - [0, 10]
```

- 至少 3 个点
- 当前后端 YAML 不接受 `"x1,y1;x2,y2;..."` 字符串；如果前端提供粘贴框，必须在导出 YAML 前转换为点列表

**`circle`** — 圆心和半径：

```yaml
center: [0, 0]
radius: 10
```

后端可以内部将 `circle` 离散为轮廓，但这只是实现细节，不应暴露为用户输入形式。

### 4.2 顶点方向规范

正式 YAML 可输入顺时针或逆时针点序。

- 后端会规范化为逆时针点序
- 倒角半径仍按用户输入顶点顺序解释；规范化时同步重排半径
- 错误路径仍应尽量定位到用户输入的角序号

### 4.3 各形状支持的几何类型

| 形状         | `polygon` | `circle` |
| ------------ | :-------: | :------: |
| `base_shape` | ✓         | ✓        |
| `rings`      | 后续      | 后续     |
| `via`        | 后续      | 后续     |

## 5. 形状定义

### 5.1 `base_shape`

`base_shape` 是当前 MVP 唯一支持的 shape 类型，生成一个实心基础图形。

**字段：**

```yaml
type: base_shape
geometry_type: polygon | circle
layer: [layer_num, datatype]
# 基础几何参数（vertices 或 center/radius）
fillet: ...
```

当前 MVP 不支持 `zoom` 字段。

**`polygon` 型支持：**

- 顶点定义、圆弧倒角（每角独立半径）

**`polygon` 型不支持：**

- 顶点量化配置、adaptive 倒角

**`circle` 型支持：**

- 圆心和半径定义、单值 `zoom`

**`circle` 型不支持：**

- 手工输入倒角；前端倒角区域显示但置灰，YAML 中倒角字段写为 `null`

---

### 5.2 `rings`

`rings` 当前不在 MVP 后端 YAML 协议中。后续实现时需要单独定义字段、偏移规则、
倒角规则和测试，不应在当前正式 YAML 中提前接受 `type: rings`。

---

### 5.3 `via`

`via` 当前不在 MVP 后端 YAML 协议中。后续实现时需要单独定义内外边界生成、布尔差、
倒角顺序和测试，不应在当前正式 YAML 中提前接受 `type: via`。

---

## 6. 倒角规范

### 6.1 倒角类型与适用范围

当前 MVP 只保留一种倒角：**圆弧倒角**。

适用范围：

- 当前已实现范围：polygon 型 `base_shape`
- 后续范围：`rings`、`via` 的倒角需要等对应 shape 类型进入 MVP 后再设计和实现
- 所有基于 `circle` 的图形，倒角字段统一写为 `null`（circle 没有用户可见的离散角，不应暴露伪造出来的角倒角配置）
- 不保留 adaptive、直线切角或多倒角模式

### 6.2 总体规则

- 倒角半径必须能独立控制每一个角
- 正式 YAML 中倒角必须写成显式列表，不允许只保留简写值
- 前端可支持单值输入和批量填充，但最终必须展开为正式结构
- YAML 中 `mode` 可省略；若保留，唯一合法值为 `arc`
- 算法同时支持凸角和凹角，始终输出切点之间的小圆弧

### 6.3 精度策略

倒角精度可作为可选图形配置项暴露给用户。未指定时，由系统根据倒角半径自动决定：

| 倒角半径      | 精度       |
| ------------- | ---------- |
| `<= 20um`     | `0.001um`  |
| `> 20um`      | `0.01um`   |

如果用户显式指定倒角精度，则以用户指定值为准。后续可能调整阈值或增加精度档位，实现上应设计为独立策略。

### 6.4 `base_shape` polygon 的倒角

仅适用于 polygon 型 `base_shape`。

- YAML 中倒角列表长度必须与角数量一致
- 列表第一个值对应 polygon 第一个点所在的角，后续依次对应
- `radius < 0` 非法
- `radius == 0` 表示该角不倒角
- 正半径不能用于共线角
- 相邻两个角的切点距离之和必须小于对应边长

五边形示例：

```yaml
fillet:
  radii: [a1, a2, a3, a4, a5]
  precision: null
```

前端简化规则：用户输入单值 `a`，展开为 `[a, a, a, a, a]`。

### 6.5 `via` / `rings` 的倒角

当前 MVP 未实现 `via` / `rings`，因此也不定义其倒角 YAML。后续实现时应复用“显式角对象/显式半径列表”的原则，但不能在当前协议中提前暴露未实现字段。

## 7. GDS 输出

### 7.1 基本输出

当前阶段只需要从 GUI/YAML 生成新的 GDS，不需要读入已有 GDS 后继续加工。

### 7.2 整体缩放

当前 MVP 不支持 `gds.scale`。整体缩放保留为后续需求，进入实现前需要先明确它与 `dbu`、坐标单位和 GDS 网格的关系。

## 8. 前端规范

### 8.1 界面统一性

- `polygon` 和 `circle` 尽量共用同一套表单结构
- `rings` 和 `via` 先选基础几何类型，再显示对应输入区
- 不适用字段尽量置灰，而不是彻底隐藏

### 8.2 简化输入与展开

前端需要支持单值输入、批量填充、自动展开为正式 YAML 列表。后端不负责保留这些交互层面的简写输入。

### 8.3 GUI 元数据

GUI 元数据应以 YAML 注释形式输出：

- 元数据不进入正式业务字段
- 后端不依赖这些元数据

### 8.4 GDS 反向读取工具

前端需要提供一个工具页或弹窗，用于读取现有 GDS 并提取图形轮廓。

**目标：**

- 上传 GDS 文件
- 输出每个图形的顶点列表（顺时针）
- 结果可直接用于后续生成 YAML

**输出内容至少包括：**

- 所属 layer
- 顶点列表

**约束：** 如果读取过程中无法稳定区分同一 layer 内的多个独立图形，则引入约束「每个
layer 只能有一个图形」。不满足该约束时，工具应报错或提示，而不是猜测。

## 9. 边界与优先级

### 9.1 明确不保留的旧能力

- `star` 生成器
- adaptive 倒角
- 复杂字符串规则解析
- 顶点精度量化作为用户配置项
- 从已有 GDS 继续叠加生成的主流程
- 复杂的历史派生元数据链
- 将 GUI 元数据写入正式业务 YAML 字段

### 9.2 低优先级需求

低优先级但建议预留：

- `layer_mapping` 的真实实现
- layer name 在 GUI 中的展示与编辑
- YAML 注释保留策略
- `base_shape_id` 的最小关联设计
- GDS 读取工具的复杂异常处理

---

## 10. 总结

重构后的 Summer-GDS 应是一个以 GUI 为主入口、以结构化 YAML 为正式协议的 GDS
生成系统。

当前 MVP 聚焦 `base_shape`、`polygon` / `circle` 两类基础几何、结构化 YAML、
polygon 每角独立圆弧倒角和 GDS 输出。`rings`、`via`、整体缩放和更复杂的前端简化输入
保留为后续迭代；进入实现前必须先更新 YAML 协议和测试设计。
